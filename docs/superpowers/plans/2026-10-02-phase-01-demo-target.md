# Phase 1: Demo Target (checkout-service) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development or superpowers:executing-plans. Steps use checkbox syntax.

**Goal:** A realistic, reproducible system with a planted latency regression, matching logs/metrics/traces in Postgres, a deterministic benchmark, and machine-readable ground truth.

**Architecture:** `demo_target/checkout-service/` is a stdlib-only Python service (sqlite3 DB, TTL cache, serializer) whose latency is measured by a deterministic **cost meter** (simulated ms per DB query / cache op / serialization), not wall-clock, so benchmarks are repeatable and sandbox-friendly. Its ~20-commit git history is generated by a script (`demo_target/history.py`) with fixed authors/dates, into a gitignored `demo_target/build/` dir, so SHAs are stable. A seeded data generator produces logs/metrics/spans/deployments around the bad deploy and loads them into Postgres.

**Tech Stack:** Python 3.12 stdlib for the service; psycopg 3 for the loader (new dependency: needed by all Postgres work, logged as D-007); pytest.

**Spec:** ROADMAP.md Phase 1; master plan.

## Global Constraints
- No git on the outer project. Git runs only inside `demo_target/build/…` with `GIT_CONFIG_GLOBAL=/dev/null`, explicit author/committer env, fixed dates.
- Service must be dependency-free (stdlib + pytest) so it runs in the Phase 3 sandbox.
- Benchmark is deterministic: same commit → identical numbers.
- `GROUND_TRUTH.json` is machine-readable and checked in.
- Regression is subtle but findable by logs/metrics/traces + code; includes a red herring and noise.

## Review Focus
- Benchmark nondeterminism (dict ordering, time, random without seed) → test runs it twice and compares.
- History build run twice produces identical SHAs → test.
- Data generator reproducible by seed; different seed differs; timestamps stay within window → tests.
- Red herring must NOT be fixable to satisfy the p95 gate (fixing it alone leaves p95 regressed) → test via benchmark on a "red-herring-only fix" tree.
- Loader idempotent (re-seed doesn't duplicate) → integration test (skips if Postgres is down).

## File Structure
```
demo_target/__init__.py
demo_target/checkout-service/        # the seeded service (source of truth is history.py; this dir is not committed as a tree)
demo_target/history.py               # ordered commits: message, date, {path: content}
demo_target/build_repo.py            # builds demo_target/build/checkout-service git repo; writes build/commits.json
demo_target/datagen.py               # pure seeded generation of deployments/logs/metrics/spans
demo_target/seed.py                  # schema + idempotent Postgres loader + CLI
demo_target/GROUND_TRUTH.json
tests/demo_target/test_history.py
tests/demo_target/test_service_benchmark.py
tests/demo_target/test_datagen.py
tests/demo_target/test_seed.py       # integration (needs Postgres)
```
(Service files are authored as `history.py` step contents; `build_repo.py` materialises them. A convenience checkout of HEAD is produced at `demo_target/build/checkout-service`.)

---

### Task 1: Service + history + build script
Deliverable: `python -m demo_target.build_repo` produces a 20-commit repo; HEAD tests pass; commit #14 introduces N+1 + cache bypass in `catalog.py`.
- Cost constants (ms): db query 2.0 + 0.05/row; cache get/set 0.1; serialize 0.5 + 0.01/item; audit query 40.0, run on every 25th request (red herring: affects p99 only, identical before/after).
- Interfaces: `checkout.service.handle_checkout(ctx, cart_id) -> dict`; `ctx.meter.ms`, `ctx.meter.db_queries`; `benchmark.py --json` → `{"requests","db_queries","p50_ms","p95_ms","p99_ms"}`.
- Tests: service unit tests live in the repo (`tests/`); outer tests build the repo and run them + assert two builds give identical SHAs.

### Task 2: Benchmark gate behaviour
Deliverable: outer test builds repo, runs benchmark at commit 13 (good), 14+ (bad), and a synthetic "good + red-herring-only fix" tree; asserts bad p95 ≥ 2.5× good; good ≈ fix-after; red-herring-only fix p95 still ≥ 2× good; benchmark twice identical.

### Task 3: Data generator
Deliverable: `generate(seed, commits, window)` → `{deployments, logs, metrics, spans}` lists of dicts. Latency steps up at last deploy (p95 ≥ 3× before); request logs carry `db_queries` (~2 → ~8); traces show per-product `catalog.get_product` db spans after the deploy; red herring `inventory_audit` slow-query warnings at the same rate before/after; unrelated redis-timeout error burst ~6h before deploy; an earlier benign deploy.

### Task 4: Postgres loader
Deliverable: `seed.py` creates tables `deployments, logs, metrics, spans` (indexes on ts, trace_id), loads idempotently (truncate+insert in one transaction), CLI `uv run python -m demo_target.seed`.

### Task 5: Ground truth + acceptance
Deliverable: `GROUND_TRUTH.json` (root cause commit sha/subject/file, symptom, acceptable fixes, red herring, deploy ts, benchmark thresholds); test that sha matches the build. Human-findability check: SQL queries (compare windows, trace drilldown) documented in `demo_target/README.md` and executed in the acceptance run.
